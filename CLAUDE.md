# `graph-m365` — local M365 MCP server

Operational summary and design doc for the server.

> The FastMCP server is named `graph-m365` and is registered in Claude Desktop under the same key. The `~/.config/<name>/` cache directory (and, with the `cli` backend, the Keychain service name) defaults to `graph-m365` as well, but is overridable via `KEYCHAIN_SERVICE`. Set it to reuse a cache created under a different name when migrating an existing install, since a rename would otherwise force a re-auth round.

---

## State

Single-file stdio MCP (`server.py`, FastMCP) over Microsoft Graph `v1.0`, exposing mail and personal-calendar tools to a Claude Desktop / Claude Code host.

Tools, by capability:

| Cap (env)     | Default | Tools registered                                                                                  | Scope added            |
|---------------|---------|---------------------------------------------------------------------------------------------------|------------------------|
| `MAIL_READ`   | `1`     | `list_messages`, `search_messages`, `get_message`, `triage_messages`, `list_mail_folders`, `unsubscribe_scan`, `unsubscribe_targets`, `list_attachments`, `get_attachment` | `Mail.Read`            |
| `MAIL_WRITE`  | `1`     | `archive_message`, `move_messages`, `delete_messages`, `mark_messages`                            | `Mail.ReadWrite`       |
| `MAIL_DRAFT`  | `1`     | `create_draft`                                                                                    | `Mail.ReadWrite`       |
| `MAIL_SEND`   | `0`     | `send_message` (dark)                                                                             | `Mail.Send`            |
| `CAL_READ`    | `1`     | `list_events`, `get_event`                                                                        | `Calendars.Read`       |
| `CAL_WRITE`   | `1`     | `create_event`, `update_event`, `delete_event`                                                    | `Calendars.ReadWrite`  |
| (always)      |         | `diagnose`                                                                                        | none                   |

`MAIL_SEND` is the only capability dark by default: requesting `Mail.Send` may trigger a separate admin-consent round, so it stays off unless explicitly enabled (see the re-seed note under Credentials). The mail read tools (`list_messages`, `search_messages`, `get_message`, `triage_messages`, `list_mail_folders`, `unsubscribe_scan`, `unsubscribe_targets`, `list_attachments`, `get_attachment`) carry inline `@mcp.tool()` decorators and register unconditionally; they consume `Mail.Read`, which `MAIL_READ=1` requests by default. `excluded_recent_count` registers only when `EXCLUDE_FOLDERS` is non-empty, and `save_attachment` registers by default with its root at `~/Downloads`, unless `ATTACH_SAVE_DIR` is empty or `off`; both ride on `Mail.Read`. `diagnose` registers unconditionally and consumes no scope: it never touches the mailbox.

**Diagnostics.** `diagnose` (and `server.py --diagnose`, the same checks from a shell) returns one row per check: resolver API (`getaddrinfo` on the login host), direct DNS (a stdlib UDP query to the first `resolv.conf` server, then 1.1.1.1, bypassing the resolver API), TCP reach to the login host, token cache (file present, mode, account and refresh-token counts, access-token expiry; never contents), clock skew against the `Date` header of a HEAD to Graph by literal IP, and host context (the parent process chain plus whether `scutil --dns` has output). It exists because of the 2026-10-05 incident in `ROADMAP.md`: a Claude Code background host spawned the server into a process tree where only the system resolver API was dead, and the server reported a bare `NameResolutionError` for an hour. The same first three checks run inline when MSAL raises `requests.exceptions.ConnectionError` in `_token()` or httpx raises `ConnectError` in `_req()`, so the error a caller sees says which layer failed ("resolver API failed, direct DNS works" versus "no route"). Direct DNS is diagnostic only: do not wire it in as a fallback resolver, which would hide a broken host instead of reporting it.

**One MSAL application and one HTTP client per process.** `_app()` builds a single `PublicClientApplication` on first use (`_APP`), with `instance_discovery=False` because the authority is a known single-tenant `login.microsoftonline.com` URL. MSAL's `Authority.__init__` fetches the tenant's OpenID configuration eagerly at construction, so this is the one request the login host sees per process; until 2026-10-05 the server built a new application per `_token()` call and so contacted the login host on every tool call even with a warm cache. Measured over ten `list_messages` calls with a warm access token: 11 login-host requests and 6.6 s before, 1 request and 0.9 s after. A warm access token now reaches Graph with no login-host traffic, so a login-host outage no longer takes down reads. Sharing the object is safe because `PersistedTokenCache` carries the state and already reloads across processes through the signal file (`tests/test_integration.py` covers that path). A failed construction leaves `_APP` unset so the next call retries. `_req` likewise sends through one module-level `httpx.Client` (`_HTTP`) so connections to Graph are reused; the 30 s timeout and the retry loop are unchanged. `msal>=1.21` is pinned in every PEP 723 header because earlier releases reject `instance_discovery`. Do not go back to per-call construction, and do not add a disk-persisted MSAL `http_cache` to shave the one remaining request: that would be a second file in the credential directory for a non-secret document, not worth the surface.

**Daemon and shim (optional).** `server.py --daemon` runs this same FastMCP server as one long-lived process listening on a Unix socket, `~/.config/<KEYCHAIN_SERVICE>/mcp.sock`, created 0600 inside the 0700 credential directory; it never opens a TCP port. Each accepted connection is checked against the daemon's own uid (`LOCAL_PEERCRED` on macOS, `SO_PEERCRED` elsewhere) and then served as one MCP session, with its own `initialize`, through `mcp.server.stdio.stdio_server` fed by two small adapters over the anyio socket stream. Sessions run concurrently in the event loop, but tool bodies are synchronous, so a Graph call in one session stalls the others for its duration: two hosts queue, which is the intended capacity. One daemon per credential directory is enforced by an exclusive `flock` on `mcp.sock.lock`, held for the daemon's lifetime; `SIGTERM` unlinks the socket and releases it. The daemon refuses to start on any backend but `file`, because a long-lived process on a Keychain backend is the August 2026 failure. `server.py` with no flags, which is what both hosts invoke, is first a **stdio shim**: a stdlib-only block at the top of the file, ahead of every third-party import, that connects to the socket if it exists, bridges stdin/stdout to it byte for byte, and exits. The shim touches no credential, resolves no name and imports neither MSAL nor httpx (`tests/test_daemon.py` asserts this with `-X importtime`), which is the exact set of things the Claude Code background host could not provide on 2026-10-05. With no socket it falls through to the in-process server, so nothing regresses when the daemon is not installed; but if the daemon's lock is held and the socket cannot be reached it exits 1 rather than start a second server on the same token cache, since two processes rotating one refresh token is how a store goes stale. Any flag (`--direct` is the documented one) skips the shim. `launchd/org.wardlaw.graph-m365.plist` is the template LaunchAgent (`RunAtLoad`, `KeepAlive`, log to `~/Library/Logs/graph-m365.log`, metadata only: the daemon's own lifecycle lines plus SDK warnings and errors; the SDK's per-request INFO chatter is raised to WARNING, and its thirty-line validation dump for Claude Desktop's unknown `server/discover` request is dropped by a root-logger filter while the JSON-RPC error reply it provokes is unchanged); `launchd/install.fish` renders it from the Desktop config's `env` block via `launchd/render_plist.py` and bootstraps it in the GUI session. Capability flags belong to the daemon, since it decides which tools exist; the host `env` blocks matter only for the fallback. The acceptance test runs the shim under a `sandbox-exec` profile that denies every network capability except the one Unix socket, where `getaddrinfo` fails exactly as in the incident, and completes a session with `diagnose` reporting a healthy resolver from the daemon's context.

**Write surface is batched-only.** `move_messages`, `delete_messages`, `mark_messages` each take a list of ids (pass one for a one-off); there are no singular `move_message`/`delete_message`/`mark_message_read` *tools* — `move_message` survives in code solely as an internal helper for `archive_message`. The plurals subsume the singulars (a one-element batch is valid) while adding `/$batch` chunking and throttle resilience, so exposing both was pure redundancy. Each runs Graph `/$batch` in chunks of 20 and returns `{requested, ok, failed[]}`, where `failed[]` carries per-item status (a per-sub-request `429` surfaces here for selective re-issue) — note a single-item failure is reported in `failed[]`, not raised. `_req` honors `Retry-After` on `429`/`503` with bounded backoff so bursts degrade gracefully. The handle/id echo the singulars used to return is no longer load-bearing: `Prefer: IdType="ImmutableId"` keeps a moved message's id stable, so the original handle stays valid.

**Stable ids.** A global `Prefer: IdType="ImmutableId"` makes message ids stable across folder moves and process restarts (must be global — mixing id formats in one process makes Graph reject the foreign id). Ids leave the server as short deterministic **handles** (`blake2s`, 8 hex chars), not raw ~152-char base64; a process-lifetime `_handle`↔`_resolve` map translates back at the action boundary. Scans drop `bodyPreview` — classification needs only sender + subject; bodies are opt-in via `get_message`/`triage_messages`. Scan `$top` is clamped to `_MAX_TOP=200`.

**Folder discovery.** `list_mail_folders` walks the folder tree (depth ≤ 4) and returns folder handles that address a folder on **both** paths: as a `move`/`move_messages` destination, enabling routing into custom folders, and as the `folder` argument to `list_messages`, `triage_messages`, and `unsubscribe_scan`, enabling reads of custom folders. It respects `EXCLUDE_FOLDERS` (excluded subtrees omitted, fail-closed).

The two paths resolve differently because Graph accepts the identifier in different positions. On the write path the destination goes in the JSON body as `destinationId`, where Graph takes a handle-resolved id or a well-known name interchangeably, so `move_messages` calls `_resolve` directly. On the read path it becomes a URL segment (`/me/mailFolders/{id}/messages`), where Graph accepts **only** a well-known name or a full id; a handle there returns `ErrorInvalidIdMalformed`. Read tools therefore go through `_folder_ref`, which resolves the handle, rejects an 8-hex string that is not a live handle with an instruction to re-run `list_mail_folders` (handles are process-lifetime, and passing a dead one through would produce the same opaque 400 this helper exists to prevent), and applies the `EXCLUDE_FOLDERS` gate to the *resolved* id. That last step is load-bearing: a handle matches neither an id nor a display name, so gating on the caller's raw string would let a handle slip the fail-closed guarantee. Well-known names (`archive`, `junkemail`, `deleteditems`) aren't in the handle map and pass through on both paths. Do not reintroduce a raw `{folder}` interpolation on a read path.

Display names are **not** accepted as a folder reference on either path. `_excluded_folder_map` builds a name→id map but only of top-level folders, while `_walk_folders` recurses to depth 4, so wiring it in would silently fail to resolve nested folders. Supporting names correctly needs a recursive cached map plus duplicate-name handling; until then, resolve names to handles via `list_mail_folders`.

**One dial, two effects.** With a capability unset, its tool is not registered AND its scope is not requested. This invariant (tool surface = requested scopes) is enforced by `CAPS` → `required_scopes()` in `server.py`; do not bypass it. Requested scopes are the union over enabled caps; the AAD-consented grant is only the ceiling.

**Server-level instructions** (`FastMCP(..., instructions=...)`) declare the read-and-stage design and the personal-calendar scoping. Tool docstrings reinforce design intent at the point of decision for `create_draft` and `delete_messages`. Calendar tool docstrings flag the invite/cancellation semantics that come with `attendees`.

**Body shape.** `get_message` returns the body as Markdown via `html2text` (link targets preserved as `[text](url)`, images/tracking pixels stripped, no hard wrap). It accepts `mode='unique'` (default — Graph's `uniqueBody`, just the new content) or `mode='full'` (whole message including quoted thread history). Plain-text bodies pass through untouched, except a text/plain body that is actually HTML (`_looks_like_html` re-sniff) is still flattened. `list_messages`/`search_messages` no longer emit `bodyPreview` — scan is metadata-only; use `triage_messages` for sanitized, head-capped bodies in one call, or `get_message` for one. `get_event` applies the same sanitizer to event bodies (Teams/Zoom join-link boilerplate) with an opt-in `head_chars` cap. Both `get_message` and `get_event` accept `links=True`, which adds a `links: [{text, url}]` list harvested from the html2text output *before* `_postclean` runs (deduped by URL, document order, capped at `_LINK_CAP=40`). This is the sanctioned way to recover a long legitimate link (Microsoft Forms, SharePoint, RSVP pages) that the URL-length / tracker heuristics correctly strip from the body; the body itself is never returned raw, and the heuristics stay as they are. Do not add a raw-body mode.

**Unsubscribe reads headers, not bodies.** `_postclean`'s `max_url_len` / `_TRACKER_PARAMS` heuristics destroy in-body unsubscribe links — correctly, since those URLs are exactly the tracker-laden kind the strip exists to kill. Do **not** relax them to recover unsubscribe links; that trades away the token reduction this server delivers. `List-Unsubscribe` / `List-Unsubscribe-Post` (RFC 2369 / RFC 8058) are *headers* and never enter the sanitizer, so `_unsub_from_headers` reads them from `internetMessageHeaders` instead. Graph returns raw `[{name, value}]` — unlike JMAP's `header:List-Unsubscribe:asURLs`, there is no server-side parsing — so the angle-bracket list is parsed locally, with a comma-split fallback for senders that omit the brackets (Slack does). `one_click` is gated on an `http` target being present: senders emit `List-Unsubscribe-Post` with no parseable `List-Unsubscribe`, and a bare `one_click` with nothing to POST to would be a lie.

Discovery is a separate tool, not a flag on `triage_messages`. The cheap route — `singleValueExtendedProperties` against `PS_INTERNET_HEADERS`, which would return just this one header — resolves to nothing on Exchange Online (verified: 0 of 14 known-positive messages). The only working collection-level path is `$select=internetMessageHeaders`, which pulls the entire header block: measured at +143% wire payload on a 50-row `triage_messages` sweep (464 KB → 1,129 KB) to compute one boolean. That cost belongs on `unsubscribe_scan`, which pulls no bodies and so sweeps several hundred messages for comparable cost, not on the hot triage path. `triage_messages` is unchanged and must stay that way.

Both tools are read-only: they report unsubscribe targets and never fire them. Firing `mailto:` targets, and POSTing to one-click endpoints, is deliberately out of scope.

**Folder exclusion.** `EXCLUDE_FOLDERS` (comma-separated; set in the Desktop `env` block) names top-level folders that are hard-excluded from `list_messages`, `search_messages`, `get_message`, `unsubscribe_scan`, and `unsubscribe_targets`. Default in code is empty so the server.py file carries no mailbox-specific data. Resolution is by display name, done once per process on first read-tool call; any unmatched name raises and refuses to read (fail-closed). The gate is folder-membership only — no content scrubbing — and is read-path only. Write tools (`move_messages`, `delete_messages`) are not source-gated; moving an excluded message into a non-excluded folder is a known, accepted way to surface it. When `EXCLUDE_FOLDERS` is non-empty, a metadata-only `excluded_recent_count(hours=24)` tool is registered alongside the gate; it returns per-folder counts of recent arrivals (via `$count` + `$filter` on `receivedDateTime`) and never returns ids, subjects, previews, or bodies.

## AAD app registration

The server expects a **public-client** AAD app registration with **delegated** Microsoft Graph permissions consented for the target tenant. `GRAPH_CLIENT_ID` and `GRAPH_TENANT_ID` (set in the host `env` block) point at it. Single-tenant authority: pass the tenant id, not `common`.

- Required delegated scopes correspond to enabled `CAPS`: `Mail.Read`, `Mail.ReadWrite`, `Mail.Send`, `Calendars.Read`, `Calendars.ReadWrite`. The server never requests `*.Shared`.
- No client secret. Public-client redirect URI must be configured (MSAL listens on a localhost port during `--auth`).
- If the tenant requires admin consent, get the grants consented once before first `--auth`. After that, toggling a capability on (changing `CAPS`) works on the next silent acquisition without re-auth, because MSAL can mint a token for any consented scope from the existing refresh token. If silent ever fails after a new toggle, re-run `--auth` once.

## Credentials

The MSAL token cache (which holds the refresh token) lives, by default, in a **0600 file** at `~/.config/<KEYCHAIN_SERVICE>/cache.json` (`SecureFilePersistence`), because the login Keychain is unreadable from any non-GUI audit session (SSH, Remote Control, launchd, the Claude Code background daemon): unlock state is per audit session and securityd cannot prompt there, so every read fails with -25308. Seeding from an existing Keychain cache happens automatically, once, on the first GUI-session launch that finds the file absent, and is one-way: the refresh token rotates on use, so only the file is live afterwards.

With `KEYCHAIN_BACKEND=cli` the cache lives in the **macOS login Keychain** instead:

- Service: value of `KEYCHAIN_SERVICE` (default `graph-m365`; see header note)
- Accounts: `default-mailbox` holds chunk 0 of the cache; further chunks are `default-mailbox.1`, `.2`, and so on. Each has a `.staged` twin (`default-mailbox.staged`, `default-mailbox.staged.1`, ...) that exists only during a write, or until the next one after a crash.
- Inspect: `security find-generic-password -s graph-m365 -a default-mailbox` (adjust `-s` if `KEYCHAIN_SERVICE` is set). This shows chunk 0 only, whose value is `v2:<n>:<base64>`; `<n>` is how many items the set spans.

On disk under `~/.config/<KEYCHAIN_SERVICE>/`: `cache.json` (the token cache, file backend only, 0600), `cache.signal` (+ `.lockfile`), the non-secret marker for `PersistedTokenCache` reload coordination. That directory must remain outside any repo or synced folder, and out of backups (`tmutil addexclusion`). **The cache file lives there and nowhere else**: never point `CACHE_FILE` into the repo (the old `token_cache.json` in the working tree is the thing that must not return), never log its contents, and never copy it to another machine; re-auth there instead.

**With the `cli` backend, Keychain access goes through `/usr/bin/security`, not the in-process client.** `_build_cache()` uses `CliKeychainPersistence`, which shells out to `security` for every read and write of the MSAL cache. The reason is a failure mode that killed several long-lived server processes in August 2026: Security.framework's legacy keychain client caches records per process and refreshes them only from change notifications delivered over a CFRunLoop, which this stdio server never runs. After a device lock the cached record handle goes stale (`CSSMERR_DL_INVALID_RECORD_UID`), every later read fails, and the process never recovers. Nothing that stays in process fixes it: a fresh `Keychain()`, a fresh `PersistedTokenCache` and `SecItemCopyMatching` all route back to the same client. Each access is therefore a fresh `security` process with a fresh cache. Cost is one process per item per load and roughly four per item per save (about 30 ms each, so 136 ms to read a 16 KB value and 322 ms to write it; a real cache spans two items), against roughly one load per signal-file bump and one save per token refresh.

Four details are load-bearing:

- **Writes go through a staging account, never `add-generic-password -U`.** Two measured facts (2026-08-28) shape `save()`. Overwriting an item in place goes through `SecKeychainItemModifyAttributesAndData`, whose ACL check `/usr/bin/security` does not satisfy even as the item's own creator: it raises a GUI prompt no server process can answer, and the call hangs to the 15 s timeout. So a write has to be delete-then-add. But while any Keychain dialog is pending anywhere on the machine, `security` reads and deletes still succeed while every *create* blocks, so a naive delete-then-add would destroy the cache and then be unable to rewrite it, costing a re-auth round. `save()` therefore writes the value to the `<account>.staged` set first: if creates are blocked it fails there with the live set untouched, and if the second write fails the value is still in staging, where `load()` picks it up. `PersistedTokenCache` holds `CrossPlatLock` across the whole sequence.
- **The value is split across items, because `security -i` truncates silently at 4096 bytes.** Its interactive mode reads a command into a 4096-byte line buffer (measured exactly: 4096 including the newline stores whole, 4097 splits). Past that it does not fail cleanly. It creates the item holding a *truncated* value and parses the tail as a second command, which surfaces only as an `unknown command` line. A real MSAL cache base64-encodes past that ceiling, so a single-item write could never store one: this is the bug that made the first cut of the CLI backend unusable, and it hid because the round-trip test used a short payload. `save()` therefore sizes chunks against `_LINE_LIMIT` and writes chunk 0 as `v2:<n>:<data>` under the bare account name, chunk *i* under `<account>.<i>`. `_add()` independently refuses any command that would exceed the limit, so the silent-truncation path cannot come back. The cost is that a live write is no longer a single delete-then-add: `_read_set` reports a set whose header promises absent items as missing rather than short, which routes a torn live set to the staging copy.
- **The secret never reaches argv.** `-w <value>` on a command line is readable through `ps`, so the add is fed to `security -i` on stdin instead. The value is stored base64-encoded, which keeps quotes and whitespace out of the interactive tokenizer. `load()` also accepts the two older layouts, a single unchunked base64 item and a bare JSON value, so an item written by an earlier build or by the old `KeychainPersistence` reads back with no re-auth.
- **`-T /usr/bin/security` at create** keeps `security` on the new item's ACL, so later reads do not prompt. The converse holds: once the CLI backend has rewritten the item, `KEYCHAIN_BACKEND=msal` will prompt, because the Python interpreter is no longer on the ACL.

Exit-status handling follows the tool, not intuition: `security` writes to stderr on success too (`password has been deleted.`), so the exit status is the signal, plus the `<cmd>: returned <n>` line interactive mode emits on a failed subcommand. `find-generic-password` returns 44 for a missing item, which is `errSecItemNotFound` (-25300) truncated to a byte; that maps to `PersistenceNotFound`, i.e. an empty cache. An *unreadable staging* value maps there too, rather than to `PersistenceDecryptionError`: staging is a fallback, not the source of truth, and `PersistedTokenCache._reload_if_necessary` catches only `PersistenceNotFound`, so raising the decryption error would propagate out of every load and block the interactive re-auth that actually recovers.

`KEYCHAIN_BACKEND` selects the store: `file` (default, everywhere), `cli` (Keychain via `security`, macOS GUI sessions only), or `msal` (the in-process legacy client, kept only for A/B). There is no silent fallback in either direction: on the Keychain backends a failure raises and is never demoted to the file, and the file backend reads the Keychain only for the one-time seed when its file is absent.

Independently of the backend, `_token()` catches `KeychainError` and re-raises with the OSStatus and its Security.framework text. `msal_extensions.osx` builds that exception with no args, so `str(e)` is empty and the host would otherwise relay `Error executing tool X: ` with nothing after it, which is how the August incident presented.

**Migration** (one interactive pass in Terminal, because the item's ACL has to be recreated with `security` on it):

```fish
security delete-generic-password -s graph-m365 -a default-mailbox
env GRAPH_CLIENT_ID=<app-id> GRAPH_TENANT_ID=<tenant-id> \
    CAL_READ=1 CAL_WRITE=1 uv run server.py --auth
```

`GRAPH_CLIENT_ID` and `GRAPH_TENANT_ID` are not optional here. They live only in the host `env` block, so a terminal run inherits nothing and `_app()` raises before the browser round opens. Copy the two values out of the Desktop config (`~/Library/Application Support/Claude/claude_desktop_config.json`, under `mcpServers.graph-m365.env`). The same applies to the re-seed below.

The alternative skips the browser round: run `security find-generic-password -s graph-m365 -a default-mailbox -w` once in Terminal and click "Always Allow". The read path is then clear, but expect one more prompt at the first token refresh, when `save()` deletes the msal-created item; grant it and every later item is `security`-created and silent. Either way, restart the servers that matter (Claude Desktop, live Claude Code sessions) so they pick up the new code. Old processes keep the old backend until restarted.

Re-seed (must run in a terminal, not via the MCP host):

```fish
cd ~/code/mcp/graph-m365-mcp
env GRAPH_CLIENT_ID=<app-id> GRAPH_TENANT_ID=<tenant-id> \
    CAL_READ=1 CAL_WRITE=1 uv run server.py --auth
```

`--auth` requests exactly the scopes its `CAPS` env resolves to (`required_scopes()`), so the interactive consent round must cover the scopes the *host* will actually use — otherwise a cap that's on in the host but off at auth time only works if its scope happens to be AAD-consented already; if it isn't, silent acquisition fails later inside the host, where no interactive consent is possible. The default re-seed above mirrors the shipped Desktop config (mail on, both calendar caps on) so one consent round covers everything that ships. `MAIL_SEND` is deliberately left off: requesting `Mail.Send` may trigger a *second* admin-consent request, so it stays out of the default seed. If you want send capability now or in the future, decide that up front and add `MAIL_SEND=1` to the seed env (and the host `env` block) so it's consented in the same round; likewise drop the `CAL_*` vars here if you decide to set the flags off in the calendar tools but want them later. The point is to consent, in one interactive pass, the exact union the host will request — no more, no less.

**Claude Desktop** — `~/Library/Application Support/Claude/claude_desktop_config.json`:

```json
"graph-m365": {
  "command": "/opt/homebrew/bin/uv",
  "args": ["run", "/Users/<you>/code/mcp/graph-m365-mcp/server.py"],
  "env": {
    "MAIL_SEND": "0",
    "CAL_READ": "1",
    "CAL_WRITE": "1"
  }
}
```

Absolute `uv` path is required — Desktop does not inherit fish `PATH`.

With the daemon installed (`fish launchd/install.fish`), this same command is the stdio shim and the `env` block is used only when the daemon is down and the server falls back to running in-process. Keep the two in step: the installer copies the Desktop `env` block into the LaunchAgent, so re-run it after changing a flag here.

**Claude Code:**

```fish
claude mcp add graph-m365 -- uv run /Users/<you>/code/mcp/graph-m365-mcp/server.py
```

## Guardrails (do not violate)

These invariants are load-bearing for *this* design — a single-user, read-and-stage, own-mailbox/own-default-calendar server. If you fork toward a different goal, change them deliberately and knowingly; don't let an agent erode them by accident.

- **Mail soft delete only.** `delete_messages` uses `DELETE /me/messages/{id}` (per item, via `/$batch`). Do not implement `permanentDelete` or folder-empty.
- **Mail send stays dark** unless `MAIL_SEND=1`. Never request `Mail.Send` otherwise.
- **No `*.Shared` scopes**, ever. Single-user, own-mailbox/own-calendar only.
- **Calendar is boxed to the default personal calendar.** Only touch `/me/events`, `/me/calendar`, `/me/calendarView`. Never enumerate `/me/calendars`. Never add tools for shared calendars.
- **Attendee semantics.** `create_event` and `update_event` with `attendees` cause Outlook to send invites; `delete_event` on an organizer-owned meeting sends cancellations. Tool docstrings already say so — preserve those notes.
- **Times default to `CAL_TIMEZONE` (default `Eastern Standard Time`).** `CAL_TZ` reads that env var; `_dt` stamps `timeZone: CAL_TZ` and read paths send `Prefer: outlook.timezone="{CAL_TZ}"`. If you ever take an ISO string with an explicit offset, the offset wins (Graph behavior). Do not strip the Prefer header.
- **The token cache file is the one credential on disk, and only at `CACHE_FILE`.** `~/.config/<KEYCHAIN_SERVICE>/cache.json`, mode 0600, directory 0700, re-tightened on every save. Never relocate it into the repo or a synced folder, never log it, and keep the seed one-way: do not write the file back into the Keychain or read the Keychain after the file exists, because the refresh token rotates and two live stores guarantee one of them goes stale. Do not switch the default back to a Keychain backend: that is the choice that made the server dead from every headless session.
- **When the Keychain backend is in use, access stays out of process.** Cache reads and writes go through `/usr/bin/security` (`CliKeychainPersistence`), a write stages the value under the `<account>.staged` set before swapping the live set, and the value is chunked so no `security` command reaches its 4096-byte line buffer. Do not route the cache back through the in-process Security.framework client, do not "simplify" the write to `add-generic-password -U`, do not drop the staging step, and do not collapse the chunking back to a single item: each reintroduces a failure the server cannot recover from without a restart, a human at a dialog, or a re-auth round. The chunking one is the quietest of them, because `security` stores a truncated value rather than failing, so keep `_add()`'s length check even if the chunk sizing ever looks redundant. `KEYCHAIN_BACKEND=msal` exists for A/B only.
- **Size the credential tests like a real cache.** The 4096-byte truncation shipped because the write path was verified with a short synthetic payload, which fits one item. Any test of this layer must use a payload at least the size of a real MSAL cache (roughly 3 KB of JSON, incompressible token blobs), or it proves nothing about the path that actually runs.
- **Stdio at the host boundary.** The daemon listens only on a 0600 Unix socket inside the credential directory, accepts connections only from its own uid, and never opens a TCP port; the hosts still speak stdio to `server.py`. No HTTP transport, no multi-user assumption. The daemon runs on the file backend only, and the shim never starts an in-process server while a daemon holds the lock. (Amended 2026-10-05 from "Stdio only", knowingly, by ROADMAP.md Phase 3.)
- **No persistence of message content, and no credential outside the token cache.** Returning bodies to the MCP client (Claude) is the purpose and fine. Never write message bodies or access tokens anywhere on disk, and never write the refresh token anywhere except the MSAL cache in its configured store (the 0600 file, or the Keychain on the `cli` backend). No log lines, no stdout, no second copy.
- **Attachments are extracted in memory and returned as text; saving to disk is the one gated exception.** `get_attachment` downloads the bytes into one `bytes` object, extracts with `pypdf`, the `.docx` XML, `html2text`, or a UTF-8 decode, and returns capped text plus metadata. It never writes a file and never returns `contentBytes` or any base64, and it refuses item and reference attachments, files over `_ATTACH_MAX_BYTES`, and binary types rather than passing them through. `save_attachment` exists because spreadsheets, images, and archives have no text form and still need to reach the user; it is on by default with its root at `~/Downloads` (changed 2026-10-14: the server runs as a launchd daemon, so an opt-in env var meant editing the plist and re-bootstrapping the job, and a Mac user expects downloads there); `ATTACH_SAVE_DIR` overrides the root and an empty value or `off` unregisters the tool. It writes only under that root: `subdir` is relative with no `..` (checked after `realpath`, so a symlink out of the root is also refused), `filename` is reduced to a bare basename, the file is created `O_EXCL` at mode 0600 so nothing is ever overwritten (collisions get `-1`, `-2`), the ceiling is `_ATTACH_SAVE_MAX_BYTES` (50 MB), the excluded-folder gate applies, and the return carries path, byte count, and sha256, never the bytes. Do not widen this: no absolute paths, no caller-chosen root, no overwrite flag. Changing the exception means changing this line and the README security model together.
  The mirror image is `create_draft(attachments=[...])`, the one path that reads a local file and uploads it. Its rules run `save_attachment`'s discipline in the other direction: each entry is an absolute path (`~` expands) that must resolve, after `realpath`, to a regular non-empty file under `$HOME` or under `ATTACH_SAVE_DIR` when the host sets it (`_attach_roots`), so a symlink leading out of those roots is refused; the per-file ceiling is `_DRAFT_ATTACH_MAX_BYTES` (150 MB, Graph's own); files up to 3 MB go as one `fileAttachment` POST, larger ones through `createUploadSession` in 3.75 MiB ranges PUT to the pre-authenticated session URL without a bearer token; every path is validated before the draft is created; and if any upload fails the draft is deleted so Drafts never shows a half-built message. The return carries `{name, bytes, sha256}` per file, never the content. No env gate: the user names each file in the call and the content lands only in their own Drafts. `send_message` inherits the parameter because it calls `create_draft`; it stays dark under `MAIL_SEND=0`. Verified 2026-10-05 against Exchange Online: Graph reports an attachment `size` a few hundred bytes over the file (MIME headers), and `DELETE` on an unsent draft bypasses Deleted Items and lands in Recoverable Items/Deletions (`recoverableitemsdeletions`), where Outlook's "Recover deleted items" finds it for the retention window. Do not widen the roots to a caller-chosen directory, and do not add a bytes-in-the-call variant.
- **Tool surface freeze.** Do not add tools beyond the twenty named in the capability table above (plus the two always-on extras: `excluded_recent_count`, which registers only under `EXCLUDE_FOLDERS`, and `diagnose`, which needs no scope and never touches the mailbox) without updating the table and routing the tool through an existing `CAPS` dial. New tools must not introduce a new scope unless a matching capability is added. Footprint must stay legible.
